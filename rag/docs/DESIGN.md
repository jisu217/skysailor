## 1. 목적

정의서 ④의 요구는 다음과 같습니다.

> 현재 침해 상황과 유사한 기존 **Gray-zone 사례, 관련 법규, 판례, 작전 절차**를 검색해 대응 판단의 근거를 제공한다. 현장 지휘관은 단순히 "위험하다"는 경보가 아니라, **과거 유사 상황에서 어떤 조치가 이루어졌고 어떤 법적·작전적 제약이 있었는지** 함께 확인할 수 있다. RAG는 **대응 수위를 정당화**하고, **과잉 대응이나 대응 지연을 줄이며**, 사람이 **더 빠르고 일관된 결정**을 내리도록 돕는다.

그래서 대응 카드는 운용자의 세 가지 질문에 답해야 합니다.

| 질문 | 카드 영역 | 근거 자료 |
|---|---|---|
| 비슷한 일이 전에 있었나? 그때 어떻게 했고 결과는? | 유사 사례 | 사례 기록 |
| 무엇이 허용되고 무엇이 제한되나? | 법적·작전적 제약 | 법령, 판례, 작전 절차 |
| 그래서 어느 수위로 대응하는 게 맞나? | 권고 대응 수위 + 근거 | 단계표 + 위 두 영역 |

## 2. 설계 원칙

| 원칙 | 내용 |
|---|---|
| 사례 중심 | 법령 조문보다 "과거에 실제로 어떻게 했는가"를 먼저 보여준다 |
| 판단하지 않음 | 위협도는 ops가 정한다. RAG는 근거를 찾고 수위를 정당화한다 |
| 범위를 넓히지 않음 | 위협 단계별 허용 범위는 고정 표로 정한다. RAG는 그 안에서 고르거나 좁히기만 한다 |
| 근거 없으면 낮게 | 근거가 부족하면 권고는 "관측 지속"이 된다 |
| 결정적 동작 | 같은 상황이면 같은 카드가 나온다 |
| 완전 오프라인 | 모든 자료와 모델은 로컬에 둔다 |
| 국가 교체 가능 | `corpus/kr`, `corpus/us`만 바꿔 국외 모드로 전환한다 |

## 3. 근거 자료와 검색

### 3.1 유사 사례 (`rag/cases/`)

**사례 기록 형식:** 사례를 문단 텍스트로 자르지 않고, 정해진 항목을 가진 기록으로 정리합니다 (`rag/cases/schema.py`, 파일 하나에 사례 하나).

| 항목 | 예시 |
|---|---|
| 일시, 지역, 시설 유형 | 2024-06, 서울·경기, 수도권 |
| 표적 유형, 수량, Remote ID | 풍선, 약 600개, 없음 |
| 취한 조치 (순서대로) | 관측 → 관계기관 통보 → 낙하 후 수거 |
| 최고 대응 수위 | 통보 |
| 결과, 부수 피해 | 재산 피해 발생 … |
| 적용된 제약 | 인구 밀집 지역 격추 시 낙하물 피해 우려 |
| 출처 | 공개 보도·공식 발표 URL |

**유사 사례 찾기:** 현재 상황과 사례의 항목을 비교해 가중 점수를 매깁니다.

```
유사도 = 3·[표적 유형 일치] + 2·[시설 유형 일치] + 1·[인구 밀집도 일치] + 1·[Remote ID 일치]
```

- 상위 3건을 보여주고, **어느 항목이 일치해서 골랐는지**(`matched_on`)를 함께 표시합니다.
- 공개 사례는 수십 건 수준이라 벡터 검색보다 이 방식이 더 정확하고 설명하기도 쉽습니다.

### 3.2 법령·판례·작전 절차 (`rag/indexing/`)

| 종류 | 예시 | 쪼개는 단위 |
|---|---|---|
| 법령 | 항공안전법, 드론 활용의 촉진 및 기반조성에 관한 법률, 전파법, 통합방위법 | 조·항 (찾을 때는 항, 보여줄 때는 조 전체) |
| 판례 | 관련 판결 | 문단 |
| 작전 절차 | 공개된 대응 지침·매뉴얼 | 문단 |

- 조각마다 법령명, 조문, 문서 종류, 국가, 시행일, 출처를 붙입니다.
- 한국어는 Kiwi로 형태소 분석을 합니다. 형태소 분석을 하지 않으면 "무인비행장치를"과 "무인비행장치"가 다른 단어로 취급되기 때문이에요.

### 3.3 검색 (`rag/retrieval/`)

```
상황 → 허용 범위 안의 각 대응 수위별 질의 생성
     → 국가·문서 종류 필터
     → 키워드 검색(BM25) 상위 20  +  의미 검색(bge-m3) 상위 20
     → 두 순위 합치기 (RRF)
     → 상위 5개
```

- 질의는 사람이 입력하지 않고 상황에서 자동으로 만듭니다. 예: 전파 차단 → "전파 차단 장치 사용 요건 무인비행장치".
- 같은 상황이면 같은 질의, 같은 결과가 나옵니다.

## 4. 대응 수위 단계표 (`rag/generation/escalation.py`)

정의서의 "대응 수위 정당화"와 "과잉·지연 감소"를 구현하는 핵심 장치입니다.

```
관측 지속 → 관계기관 통보 → 경보 발령 → 전파 차단 → 물리적 무력화
 observe      report          alert        rf_jam       kinetic
```

**위협 단계별 허용 범위 (시작값, 팀 검토로 확정):**

| 위협 단계 | 허용 범위 |
|---|---|
| LOW | 관측 |
| MEDIUM | 관측 ~ 통보 |
| HIGH | 관측 ~ 경보 |
| CRITICAL | 관측 ~ 무력화 |

**권고 수위를 정하는 규칙:**
1. 위협 단계로 허용 범위를 정합니다 (고정 표).
2. 제약에 걸리는 수위를 뺍니다. 예: 인구 밀집 지역 → 무력화 제외, 전파 차단 권한 요건 미충족 → 전파 차단 제외.
3. 남은 범위 안에서 **유사 사례가 실제로 도달한 최고 수위**를 권고합니다. 사례가 없으면 남은 범위의 가장 낮은 수위를 권고합니다.
4. 근거(사례나 조문)가 하나도 없으면 "관측 지속"을 권고하고 "근거 부족"을 표시합니다.

이 규칙 덕분에 권고는 항상 **"위협 단계 → 제약 → 사례"** 순서로 설명할 수 있습니다. 과잉 대응(범위를 넘는 권고)은 구조적으로 나올 수 없습니다.

## 5. 대응 카드 (`rag/generation/`)

### 5.1 카드 구성

```
┌ T-07 · 신원 미상 드론 · 위협 HIGH ─────────────────────────────┐
│ [유사 사례]                                                     │
│  · 2022.12 무인기 영공 침범 (표적·시설 유형 일치)               │
│    조치: 관측 → 경보 → 추적 … / 결과: …                         │
│  · …                                                            │
│ [제약]                                                          │
│  · 법적: ○○법 제○조 — "…" (원문 인용)                          │
│  · 작전: 인구 밀집 지역 → 무력화 시 낙하 피해                   │
│ [권고]  경보 발령   (허용 범위: 관측~경보)                      │
│  근거: 위협 HIGH → 범위 관측~경보 → 유사 사례 2건이 경보까지 대응 │
│ ※ AI는 선택지와 근거만 제시합니다. 최종 결정은 운용자가 합니다.  │
└─────────────────────────────────────────────────────────────────┘
```

출력 형식은 `ops/core/schemas.py`의 `Recommendation`입니다.

### 5.2 생성 방식

- **템플릿 모드 (기본):** 고정 문장 틀에 사례·조문·규칙 결과를 채웁니다. 지어낸 내용이 들어갈 여지가 없고 응답이 즉시 나옵니다.
- **LLM 모드 (나중에 선택):** 로컬 LLM이 같은 근거로 "근거" 문장만 자연스럽게 다시 씁니다. 권고 수위 자체는 4장 규칙으로 정하고, LLM은 바꾸지 못합니다.

### 5.3 인용 확인 (`rag/generation/verify.py`)

카드에 인용한 문장이 원문에 실제로 있는지 문자열로 대조합니다(공백·문장부호 정규화). 확인되지 않은 인용은 카드에서 뺍니다.

## 6. 평가

정의서가 약속한 효과를 측정하도록 설계합니다.

### 6.1 평가 시나리오 (`rag/eval/qrels.jsonl`)

시나리오 20개 내외를 만들고, 각각에 다음 정답을 팀이 정합니다.
- 적정 대응 수위
- 떠올라야 할 사례
- 근거 조문

근거가 없어야 정답인 시나리오도 몇 개 넣습니다.

### 6.2 지표

| 정의서의 약속 | 지표 | 측정 방법 |
|---|---|---|
| 유사 사례 제시 | 사례 적중률 | 정답 사례가 상위 3건 안에 드는 비율 |
| 법적 근거 제시 | 조문 적중률 | 정답 조문이 상위 5개 안에 드는 비율 |
| 과잉·지연 감소 | 과잉 / 과소 / 적정 비율 | 권고 수위를 정답 수위와 비교 |
| 일관된 결정 | 일관성 | 같은 상황 반복 입력 → 카드가 같은지 |
| 근거 신뢰성 | 인용 확인 통과율 | 5.3을 통과한 인용 비율 |
| 더 빠른 결정 | 결정 시간 | 카드 있음/없음으로 팀원 몇 명에게 소규모 테스트 |

**발표용 비교 하나:** 카드 있음/없음일 때 운용자 결정의 적정 수위 일치율과 결정 시간. 정의서 주장을 가장 직접적으로 보여줍니다.

## 7. 모델과 실행 환경

모델은 직접 만들거나 학습시키지 않고, 공개 모델을 내려받아 로컬에서 실행합니다.

| 구성 요소 | 필요 시점 | 후보 |
|---|---|---|
| Kiwi 형태소 분석기 | 1차 (필수) | kiwipiepy |
| 임베딩 모델 | 1차 (필수) | bge-m3 (다국어·한국어) |
| 생성 LLM | LLM 모드를 쓸 때만 | Qwen·Gemma·EXAONE 계열 7~9B, Ollama로 실행 |

- 의존성(kiwipiepy, sentence-transformers)은 구현을 시작할 때 `pyproject.toml`에 별도 그룹으로 추가합니다. 기존 파일 수정이라 승인 후 진행합니다.
- 모델마다 상업 이용 조건이 다릅니다. 예를 들어 EXAONE은 비상업 라이선스로 알려져 있어요. LLM을 고를 때 반드시 확인합니다.

## 8. 단순화 결정

처음 설계에서 시연 목적에 비해 과했던 부분을 다음과 같이 줄였습니다. 오른쪽 열의 조건이 생기면 다시 넣습니다.

| 처음 설계 | 바꾼 것 | 뺀 이유 | 다시 넣을 조건 |
|---|---|---|---|
| 법령 조문 검색 중심 | **사례 중심** + 법령·판례·절차 | 정의서의 핵심은 "과거에 어떻게 했는가" | — (방향 수정) |
| 대응 선택지별 카드 나열 | 3단 카드 + 권고 수위 하나 | 운용자가 한눈에 볼 수 있어야 함 | — (방향 수정) |
| 사례를 벡터 검색 | 항목 일치 점수 | 사례가 수십 건이라 이쪽이 더 정확하고 설명 가능 | 사례가 수백 건 이상이 될 때 |
| 리랭커 (bge-reranker) | 제외 | 문서 수가 적어 효과 대비 비용이 큼 | 조문 적중률이 낮을 때 |
| NLI 모델로 인용 검증 | 문자열 대조만 | 템플릿 모드는 원문을 그대로 인용함 | LLM 모드에서 바꿔 쓴 문장을 쓸 때 |
| LLM JSON 형식 강제·인용 ID 제한 | LLM은 근거 문장만 다시 씀 | 수위 결정을 규칙으로 옮겨 LLM 역할 축소 | — |
| 색인 해시 버전 관리 | 날짜 문자열 버전 | 시연 기간에 법령이 바뀔 가능성 낮음 | 장기 운영 시 |
| nDCG, MRR, ALCE 인용 지표 | 적중률, 과잉·과소 비율, 일관성 | 정의서 주장과 직접 연결되는 지표로 | 검색 성능 논문 수준 비교가 필요할 때 |
| 검색 구성 6종 비교 실험 | 카드 있음/없음 비교 하나 | 발표에서 전달력이 높은 것 하나에 집중 | 시간이 남을 때 |

## 9. 위험과 미결 사항

| 항목 | 위험 | 대응 |
|---|---|---|
| 작전 절차 확보 | 대부분 비공개라 구하기 어려움 | 공개 매뉴얼부터 조사. 못 구하면 "가상 절차 문서"임을 명시하고 사용 |
| 판례 | 드론·풍선 관련 국내 판례가 적을 가능성 | 항공·전파 관련 판례로 범위 확대, 없으면 판례 영역 축소 |
| 사례 정리 | 공개 정보만으로는 조치·결과가 불완전할 수 있음 | 확인된 항목만 기록하고 출처를 반드시 남김 |
| 허용 범위 표 | 팀이 임의로 정하면 근거가 약함 | 사례와 법령으로 각 칸의 근거를 문서화, 가능하면 외부 검토 |
| 평가 정답 | 정답 수위를 누가 정하나 | 팀원 2명 이상이 독립적으로 정하고 차이를 기록 |
| 국외 모드 | 대상 국가·문서 미정 | 한국 모드를 완성한 뒤 결정 |
