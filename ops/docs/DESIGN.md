## 1. 목적

과제:

> 도심 환경에서 소형 드론·풍선 등 저신호 비행체를 **탐지, 추적, 식별**하고 **위협도를 평가**하여 **대응 결심을 지원**하는 Gray-zone Counter-UAS 체계를 개발하라.

ops는 돔 노드가 보낸 정보(카메라 영상, Remote ID, 자세·위치)를 받아 **탐지 → 추적 → 식별 → 위협도**까지 처리하고, 대응 추천(rag)과 운용자 결정을 화면에서 연결합니다.

## 2. 설계 원칙

| 원칙 | 내용 |
|---|---|
| 화면 우선 | 단순한 분석으로 화면부터 끝까지 동작시키고, 그다음 분석을 개선한다 |
| 결정적 판단 | 위협도는 고정 규칙으로 계산한다. 같은 입력이면 같은 결과. LLM은 판단하지 않는다 |
| 근거 표시 | 식별과 위협도에는 항상 "왜 그렇게 판단했는지"가 함께 표시된다 |
| 경보 경로 분리 | 위협도 계산과 RAG 카드를 분리한다. RAG가 느려도 경보는 늦지 않는다 |
| 사람이 최종 결정 | AI는 선택지와 근거만 제시하고 실행 권한은 없다 |

## 3. 전체 흐름

| 화면 | 단계 | 핵심 기술 | 담당 |
|---|---|---|---|
| **1. 기기 성능** | ① 돔이 보기 | Remote ID 수신, 카메라 촬영 | 돔 펌웨어 (센서 팀) |
| | | 무게추 자세 제어 | 기존 코드 (`hanging.py`, Arena) |
| | | 돔 상태 평가, 바람 측정 | `ops/nodes/` |
| **2. 표적 판단** | ② 찾기 | 영상 객체 검출 AI, 카메라 방향 보정 | `ops/perception/` |
| | ③ 위치 계산 | 삼각측량 | `ops/localization/` |
| | ④ 추적 | 칼만 필터, 측정–궤적 연결, 센서 융합 | `ops/tracking/` |
| | ⑤ 식별 | 영상 분류 + 바람 대비 궤적 분류 + Remote ID 허가 확인 | `ops/assessment/classify.py` |
| | ⑥ 위협도 | 위협도 점수화, 풍선 낙하 예측 | `ops/assessment/threat.py`, `footprint.py` |
| **3. 대응 결심** | ⑦ 대응 추천 | 오프라인 RAG, 대응 수위 단계표, 부수 피해 비교, 국외 모드 | `rag/` |
| | ⑧ 결심 | 골든타임, 사람 결정 + 결정 기록 | `ops/service/` |

```
돔 ──영상──▶ ② 검출 → 방향 ─┐
   ──IMU───▶ (방향 보정)     ├─▶ ③ 삼각측량 → ④ 추적 ◀── Remote ID (위치 직접)
   ──GPS───▶ ① 노드 상태     ┘                    │
                                                    ▼
                                ⑤ 식별 → ⑥ 위협도 ──▶ 화면 (경보)
                                                    └──▶ ⑦ rag 카드 → ⑧ 운용자 결정 → 기록
```

**협조 표적과 비협조 표적:**
- **협조 표적(허가 드론):** Remote ID로 자기 위치를 직접 보냅니다. ②③을 거치지 않고 ④로 바로 들어갑니다.
- **비협조 표적(위협 드론·풍선):** Remote ID가 없으니 카메라로 찾습니다. ② → ③을 거쳐 위치를 얻습니다.

## 4. 입력 데이터와 데이터 형식

### 4.1 입력 데이터

| 구분 | 출처 | 주요 항목 | 주기 |
|---|---|---|---|
| A. 노드 상태 | 돔 GPS·IMU | 위치, 자세(roll·pitch·yaw), 각속도, 배터리, 통신 품질, 카메라 상태 | 10Hz |
| B1. 카메라 | 돔 카메라 → 지상 | 영상 프레임 (또는 압축 프레임) | 5~15fps |
| B2. Remote ID | 돔 수신기 | 기체 ID, 위치·고도·속도·방향, 운용자 위치 | 수신 시 |
| C. 환경 | 돔 표류, 기상 관측소 | 풍향·풍속, 추정 오차 | 10초~1분 |
| D. 참조 정보 | 사전 준비 | 보호시설(위치·반경·중요도), 인구 격자, 허가 비행 목록, 공역, 지도 | 고정 |
| E. 운용자 입력 | 화면 | 결정, 사유, 추가 관측 요청 | 수시 |

### 4.2 좌표계

- 내부 계산은 기준점을 원점으로 한 **ENU(동·북·상) 미터 좌표계**로 합니다. 위경도는 입력과 지도 출력에서만 변환합니다 (`ops/core/geo.py`).
- 방향은 방위각(북쪽 기준 시계 방향)과 고각(수평 기준 위쪽)으로 표현합니다.

### 4.3 데이터 형식 (`ops/core/schemas.py`)

| 형식 | 생산 → 소비 | 핵심 필드 |
|---|---|---|
| `NodeStatus` | 돔 → ①, ② | 위치, 자세, 각속도, 안정도, 관측 범위 |
| `CameraDetection` | ② 검출 → ② 방향 변환 | 박스(px), 유형, 확신도 |
| `Detection` | ② / Remote ID → ③ ④ | 측정(방향 또는 위치 + 오차 R), 출처, 유형, Remote ID |
| `WindEstimate` | 바람 → ⑤ ⑥ | `w`, `P`(불확실성) |
| `Track` | ④ → ⑤ ⑥ 화면 | 위치, 속도, 오차, 출처, 영상 유형, 분류 확률 |
| `Threat` | ⑥ → 화면·rag | 점수, 단계, 세 요소, CPA, TTI, 근거 |
| `Recommendation` | rag → 화면 | 유사 사례, 제약, 권고 수위 |
| `Decision` | 화면 → 기록 | 결정, 대응, 사유 |

## 5. 단계별 설계

### 5.1 ① 돔이 보기 (`ops/nodes/`)

돔의 자세 제어 자체는 돔에서 합니다(기존 `hanging.py` 모델, Arena 제어기). ops는 돔이 보낸 상태를 받아 **"지금 이 돔을 믿을 수 있나"**를 평가합니다.

| 출력 | 계산 |
|---|---|
| 안정도 (0~1) | 최근 기울기와 각속도(카메라 흔들림)로 계산 |
| 관측 범위 | 카메라 탐지 거리 × 안정도 |
| 노드 경고 | 안정도 저하, 카메라 이상, 통신 품질 저하 |
| 바람 (`wind.py`) | 무동력 돔의 수평 표류 속도 ≈ 그 고도의 바람. 관측소 자료와 결합 |

안정도는 ②의 방향 오차와 ③의 위치 오차에 그대로 반영됩니다. **자세 제어 성능이 곧 탐지·위치 정확도**로 이어지는 연결 고리예요.

### 5.2 ② 찾기 (`ops/perception/`)

**검출 (`detector.py`):**
- 영상 검출은 **지상에서** 합니다. 25g 돔에서는 연산이 어렵기 때문이에요.
- 공개된 드론·풍선·조류 이미지로 미세 조정한 소형 객체 검출 모델을 사용합니다.
- 출력은 박스, 유형(드론·풍선·조류), 확신도입니다. 확신도 0.4 미만은 버립니다.

**방향 변환 (`bearing.py`):**

```
박스 중심 픽셀 → 카메라 광선 (카메라 내부 파라미터)
            → 카메라 장착 각도 + 그 순간 돔 자세(IMU)로 회전
            → 방위각·고각 [az, el]
```

- 영상 프레임과 IMU 값은 **같은 시각** 것을 써야 합니다(시각 동기, 10장).
- 방향 오차 R은 픽셀 오차와 자세 오차(흔들림)를 합쳐서 계산합니다.

### 5.3 ③ 위치 계산 (`ops/localization/`)

카메라는 방향만 알고 거리는 모릅니다. 그래서 **돔 2대 이상의 방향선이 만나는 점**을 위치로 계산합니다.

1. **묶기:** 같은 시간대(0.5초 이내)와 같은 유형의 방향선을 같은 표적 후보로 묶습니다.
2. **교차:** 방향선들과의 거리 제곱합이 최소인 점을 최소제곱으로 구합니다. 위치 오차(공분산)와 잔차를 함께 냅니다.
3. **거부:** 방향선이 거의 평행하면(교차각이 작으면) 위치 오차가 너무 커서 버립니다.
4. **돔 1대만 볼 때:** "이 방향 어딘가"로 두고 화면에 방향선으로 표시합니다. 위협도는 위치가 생길 때부터 계산합니다.

### 5.4 ④ 추적 (`ops/tracking/`)

| 구성 | 방법 |
|---|---|
| 필터 (`kalman.py`) | 등속 칼만 필터. 입력은 ③의 위치 또는 Remote ID 위치 |
| 측정–궤적 연결 (`association.py`) | 예측 위치와의 통계적 거리로 후보를 거른 뒤, 가까운 순서로 배정 |
| 궤적 관리 (`manager.py`) | 최근 5번 중 3번 잡히면 확정, 5초간 측정이 없으면 소실 |
| 센서 융합 (`fusion.py`) | 카메라 궤적이 Remote ID 위치와 여러 번 가까이 있으면 같은 기체로 합침 → 허가 여부 확인 |

### 5.5 ⑤ 식별 (`ops/assessment/classify.py`)

세 가지 근거를 합쳐 유형 확률을 냅니다.

| 근거 | 내용 | 강점 |
|---|---|---|
| **영상 분류** | ②의 유형·확신도를 궤적 단위로 평균 | 모양으로 바로 구분 |
| **바람 대비 움직임** | `v_air = v_track − w`, `T = v_airᵀ(P_v + P_w)⁻¹v_air`. 최근 5초 평균 T가 작으면 바람을 따라 흐름 → 풍선 | 영상이 작거나 흐릴 때 보완 |
| **Remote ID** | 신호가 있고 허가 목록에 있으면 허가 드론 | 신원 확정 |

- 세 근거를 서로 독립인 확률로 보고 곱해서 합칩니다(나이브 베이즈). 근거가 적을수록 "미상" 몫을 크게 남깁니다 (근거 0개 100%, 1개 35%, 2개 12%, 3개 5%).
- 영상과 움직임이 **서로 다르게 판단하면** "확인 필요"로 표시하고 근거를 둘 다 보여줍니다.
- 움직임 근거는 최근 5초가 쌓여야 씁니다. 그 전에는 "판정 대기"입니다.
- 판정 근거는 문장으로 `Track.class_basis`에 담아 화면에 그대로 보여줍니다.

### 5.6 ⑥ 위협도 (`ops/assessment/threat.py`, `footprint.py`)

```
Threat = P(hostile) × Consequence × Urgency     → 0~100

P(hostile)   ← 분류 결과, Remote ID 유무, 허가 비행 여부
Consequence  ← 가장 가까운 보호시설의 중요도, 예상 도달·낙하 지점의 인구 밀집도
Urgency      ← CPA(최근접 거리), TTI(보호구역 도달까지 남은 시간)
```

**CPA와 TTI (직선 운동 가정):** 표적 위치 `p`, 속도 `v`, 보호구역 중심 `c`, 반경 `r`일 때

```
t_cpa = max(0, −(p−c)·v / ‖v‖²)
CPA   = ‖(p−c) + v·t_cpa‖
TTI   = ‖(p−c) + v·t‖ = r 이 되는 최초의 t ≥ 0   (닿지 않으면 ∞)
```

**풍선 낙하 예측:**

```
낙하 예상 지점 ≈ 현재 위치 + 바람 × (고도 / 하강 속도)
반경            ∝ 바람 불확실성 × 낙하 시간
```

원 안의 인구를 Consequence에 반영합니다.

**새 궤적 처리:** 궤적이 막 생겼을 때는 속도 추정이 거칠어서 남은 시간이 잘못 짧게 나올 수 있습니다. 그래서 수평 속도 불확실성이 3 m/s를 넘으면 접근 방향을 쓰지 않고 위치만으로 평가하고("속도 추정 중"), 수직 속도 불확실성이 0.5 m/s를 넘으면 풍선 하강 속도를 기본값(1 m/s)으로 둡니다.

**점수:** `100 × (P × C × U)^0.7`. 낮은 구간을 넓혀서 단계 구분이 잘 되게 합니다.

**단계 구분 (시작값, 팀 검토로 조정):**

| 단계 | 점수 | 화면 |
|---|---|---|
| LOW | 0–25 | 회색 |
| MEDIUM | 25–50 | 노랑 |
| HIGH | 50–75 | 주황 + 경보 + 결정 대기열 |
| CRITICAL | 75–100 | 빨강 + 경보 + 결정 대기열 최상단 |

### 5.7 ⑦ 대응 추천 · ⑧ 결심 (rag 연동, `ops/service/`)

- **⑦:** HIGH 이상 표적의 상황 요약을 rag에 넘기면, 유사 사례·제약·권고 수위가 담긴 카드를 받습니다. 자세한 내용은 rag 설계를 보세요.
- **결정 마감:** `TTI − 여유 시간`(드론 60초, 풍선 120초)을 화면에 표시합니다.
- **⑧ 결정 기록 (`decisions.py`):** 결정마다 JSONL 한 줄로 남깁니다.
  - 결정, 대응, 시각, 경보부터 결정까지 걸린 시간
  - 그때의 위협도와 카드
  - 권고와 다르게 결정한 경우 그 사유 (입력 필수)

**API (`api.py`):**

| 엔드포인트 | 용도 |
|---|---|
| `POST /api/ops/scenario/start` | 시나리오 재생 시작 |
| `WS /api/ops/ws` | 노드·궤적·위협도 실시간 전송 |
| `GET /api/ops/recommendation/{track_id}` | 대응 카드 (rag 호출) |
| `POST /api/ops/decision` | 운용자 결정 기록 |

메인 화면에서 세 화면으로 나뉩니다. 프로토타입: [prototypes/c-uas-ops.html](../../prototypes/c-uas-ops.html)

| 화면 | 질문 | 보여주는 것 |
|---|---|---|
| **메인** | 지금 상황은? | 세 화면 요약 카드, 상황도, 이벤트 피드 |
| **1. 기기 성능** | 잘 보고 있나? | 노드별 안정도·기울기·관측 범위, 탑재 제어기(Arena 근거), 바람 |
| **2. 표적 판단** | 무엇이고 얼마나 위험한가? | 상황도(궤적·방향선·낙하 범위), 위험 순 목록, 식별 근거, 위협도 3요소 |
| **3. 대응 결심** | 무엇을, 언제까지 해야 하나? | 마감 순 결정 대기열, 유사 사례, 제약, 대응 단계표, 부수 피해, 결정 버튼, 결정 기록 |

상단 바에는 처리 단계, 경보 수, 가장 짧은 남은 시간(골든타임)이 항상 보입니다.

## 7. 진행 순서

| 단계 | 내용 | 끝났을 때 보이는 것 |
|---|---|---|
| **1차** | 시나리오(가상 노드·검출·Remote ID) + 삼각측량 + 단순 추적 + 화면 | 지도 위에서 표적이 움직이고, 돔 1대만 볼 때는 방향선으로 표시 |
| **2차** | 식별(영상 + 바람 + Remote ID) + 위협도와 근거 | 표적 색상, 위험 순 목록, 근거 표시 |
| **3차** | rag 카드 연동, 결정·기록 | 대응 결심 화면 동작 |
| **4차** | 실물 연결: 카메라 영상 검출, Remote ID 수신 | 가상 입력을 실제 입력으로 교체 |

1~3차는 가상 입력으로 진행하고, 입력 형식이 실제 센서와 같아서 4차에서 그대로 교체할 수 있습니다.

## 8. 검증

| 대상 | 확인할 것 |
|---|---|
| 좌표 변환 | 왕복 변환 오차 |
| 방향 변환 | 알려진 위치의 물체 → 계산한 방향이 맞는지, 자세 보정 유무 비교 |
| 삼각측량 | 방향선 교차 위치 오차, 교차각이 작을 때 거부되는지 |
| 추적 | 직선 표적 수렴, 교차하는 두 표적의 ID가 뒤바뀌지 않음 |
| 센서 융합 | 카메라 궤적과 Remote ID가 올바르게 합쳐지는지 |
| 식별 | 풍선·드론·조류 정확도, 영상만 / 움직임만 / 둘 다 비교 |
| 위협도 | CPA·TTI 계산, 가까워지면 점수가 내려가지 않음, Remote ID 허가 시 점수 하락 |
| 전체 | 시나리오별 탐지율, 위치 오차, 가장 위험한 표적이 1순위인지, 탐지부터 카드까지 걸린 시간 |

**발표용 비교:**
- 자세 안정도별 탐지율·위치 오차 → 결과물 ②(자세 제어)가 탐지 성능에 미치는 영향
- 식별 근거 조합별 정확도 (영상만 / 바람만 / 둘 다)

결과 저장 위치는 구현할 때 정합니다.

### 8.1 1차 시뮬레이션 결과 (가상 입력, 2026-10-10)

조건: 돔 3대(정삼각형), 돔당 카메라 8대(4K, 화각 60°, 수평 5°·위 38° 2단), 120초, 시드 0.
지표: 표적 근처(50m 이내)에 확정 궤적이 있었던 시간 비율 / 위치 오차 중앙값.

| 표적 | 돔 간격 250m | 돔 간격 700m |
|---|---|---|
| 풍선 2m (B-01, B-02) | 69~98% / 약 4m | 91~98% / 약 4m |
| 2m급 고정익 드론 (D-01) | 49~55% / 2~5m | 64~76% / 4~6m |
| **0.4m 쿼드콥터 (D-02)** | **0%** | **0%** |
| 조류 0.3m (K-01) | 0~5% | 0~4% |
| Remote ID 드론 (R-01) | 98% / 약 3m | 98% / 약 3m |
| 거짓 궤적 | 단계당 0~0.1개 | 단계당 0개 |

**알게 된 것:**
- **소형 쿼드콥터는 이 카메라로 추적되지 않습니다.** 0.4m 물체는 4K·화각 60°에서 약 110m 안쪽에서만 안정적으로 보여서(4px 기준 최대 약 330m), 두 돔이 동시에 보기 어렵습니다. 해결하려면 화각을 좁히거나(카메라 수 증가), 돔 간격을 100~150m로 줄이거나, 다른 센서와 결합해야 합니다.
- **하늘 전체를 덮으려면 돔당 카메라가 많이 필요합니다.** 화각 60° 카메라로 고각 −12°~55°를 덮는 데 8대가 필요합니다. 25g 돔 탑재 가능 여부를 센서 팀과 확인해야 합니다.
- **돔 흔들림의 영향은 생각보다 작습니다.** IMU 자세값으로 방향을 보정하면 흔들림이 대부분 상쇄되고, 남는 영향은 모션 블러(노출 1/500초 가정)와 시각 동기 오차입니다. 안정도 0.97 → 0.09에서 고정익 드론 추적률이 700m 간격 기준 75% → 64%로 떨어졌습니다. 단, 이 결과는 IMU 정확도(0.5°)와 노출 시간 가정에 좌우됩니다.
- 위치 정확도는 삼각측량이 되는 표적이면 수 m 수준입니다.

모든 수치는 가상 검출 모델(표적 크기 → 픽셀 크기 → 검출 확률)에 근거한 값이며, 실제 카메라·검출 모델로 다시 측정해야 합니다.

### 8.2 2차 시뮬레이션 결과 (식별·위협도, 가상 입력)

조건: 8.1과 같음, 돔 간격 250m. 가상 보호구역 2곳(정부청사·변전소), 인구 밀집 2곳, 허가 목록에 R-01.

| 표적 | 식별 결과 (추적된 시간 중) | 위협 단계 | 비고 |
|---|---|---|---|
| 풍선 B-01, B-02 | 풍선 100% | LOW~MEDIUM | 낙하 예상 지점의 인구에 따라 변함 |
| 2m급 고정익 D-01 | 드론 100% | 최고 CRITICAL (점수 86) | 정부청사 도달 75초 전에 처음 HIGH |
| 허가 드론 R-01 | 드론 100% | LOW 100% | Remote ID + 허가 목록 |
| 조류 K-01 | **드론으로 오분류** (추적된 10스텝) | LOW | 검출이 드물어 영상 근거가 거의 없었음 |

- 새 궤적의 거친 속도 때문에 생기던 오경보(풍선이 탐지 1초 만에 HIGH)는 속도 신뢰도 조건을 넣어 없앴습니다.
- 조류 오분류는 영상 근거가 부족할 때 움직임만으로 판단해서 생깁니다. 실제 영상 검출 모델이 들어오면 다시 확인해야 합니다. 위협도는 LOW라 경보로 이어지지는 않았습니다.

## 9. 단순화 결정

시연 목적에 비해 과한 부분은 줄였습니다. 오른쪽 열의 조건이 생기면 다시 넣습니다.

| 처음 설계 | 바꾼 것 | 이유 | 다시 넣을 조건 |
|---|---|---|---|
| IMM (움직임 모델 3개 혼합) | 등속 칼만 필터 하나 | 식별은 영상 + 바람 대비 속도로 충분 | 급기동 드론 추적이 자주 끊길 때 |
| 방향 측정을 필터 안에서 직접 처리(EKF) | **삼각측량으로 위치를 먼저 구한 뒤 칼만 필터** | 구현·디버깅이 쉽고 단계별 검증 가능 | 돔 1대만 보는 상황이 많아 방향만으로 추적해야 할 때 |
| 헝가리안 최적 배정 + JPDA | 가까운 순서 배정 (게이트 99.9%) + 2점 속도 초기화 | 시연 표적 수가 적음. 교차 시험 50회 중 ID 뒤바뀜 1회 | 풍선 다수 시나리오에서 ID가 자주 뒤바뀔 때 |
| 순차 판정(SPRT) + GBDT + 확률 보정 | 근거별 평균 + 규칙 | 실측 데이터 없이 보정은 의미가 약함 | 실측 비행·영상 데이터가 쌓였을 때 |
| 몬테카를로 침입 확률·낙하 타원 | 직선 운동 CPA·TTI, 바람 × 낙하 시간 + 원 | 시연에서 차이가 거의 안 보임 | — |
| GOSPA, ECE, Kendall τ 등 전문 지표 | 탐지율, 위치 오차, 분류 정확도, 1순위 적중 | 설명하기 쉬운 지표 | 논문·보고서 수준 평가가 필요할 때 |
| 오프라인 지도 타일 서버 | 정적 배경 지도 | 시연 지역 하나면 충분 | 지역을 자유롭게 바꿔야 할 때 |
